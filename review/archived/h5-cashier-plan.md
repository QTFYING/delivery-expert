# H5 收银台设计与接入指南

> 文档状态：讨论稿，已归档

> 版本：v0.2
> 日期：2026-04-29
> 定位：讨论稿，用于 H5 收银台页面设计、前端接入和联调验收。
> 事实源说明：支付状态、错误码和接口语义以后端 `docs/api/h5-api-doc.md`、共享枚举和服务端实现为准；本文不替代正式 API 契约。

## 1. 页面定位

H5 收银台是订单公开支付入口，面向客户扫码后完成收款动作。

H5 页面负责：

- 展示订单公开信息。
- 展示后端返回的当前收款状态。
- 发起在线支付。
- 提交线下登记备注。
- 轮询后端支付状态。
- 根据后端错误码展示对应页面状态。

H5 页面不负责：

- 自己计算应付金额。
- 自己维护支付状态机。
- 自己判断订单是否已支付。
- 自己判断二维码是否过期。
- 自己累计实收金额。
- 暴露内部部分收款、拆分收款能力。
- 感知拉卡拉、收钱吧等具体支付网关字段。

核心原则：

> H5 负责体验，后端负责事实；H5 不维护支付状态机，只消费后端状态和错误码。

## 2. 后端事实源

H5 页面所有支付状态以后端返回为准。

当前 H5 收款状态闭集如下：

| status                 | 页面含义                              | 前端行为                                                             |
| ---------------------- | ------------------------------------- | -------------------------------------------------------------------- |
| `unpaid`               | 待支付                                | 可发起在线支付，可提交线下登记备注                                   |
| `paying`               | 支付确认中                            | 展示确认中，启动轮询，禁止重复发起                                   |
| `pending_verification` | 线下登记待确认                        | 提示等待商户确认，禁止重复提交                                       |
| `paid`                 | 已完成                                | 展示付款完成，停止轮询，刷新详情                                     |
| `expired`              | 上一笔支付尝试过期，或订单已作废/过期 | 以后端返回的可操作性为准；仍在租户收款码有效期内时可重新发起在线支付 |

前端不能通过本地事件私自推进状态。例如：

- 用户点击“去支付”后，前端可以进入按钮 loading，但不能把业务状态改成 `paying`。
- 轮询多次未成功后，前端不能自己把订单改成 `expired`。
- 请求失败后，前端不能自己把订单改成失败态。
- 页面停留时间超过某个阈值后，前端不能自己判定二维码过期。

前端展示状态必须来自：

- `GET /pay/:token`
- `GET /pay/:token/status`
- 操作接口成功响应中的后端状态
- 操作接口异常响应中的后端错误码

## 3. 页面信息结构

建议页面包含以下区域。

### 3.1 商户信息区

- 商户名称。
- 客服电话。
- 可选：门店或企业展示信息。

### 3.2 订单摘要区

- 订单号。
- 客户名称。
- 下单时间。
- 当前订单状态文案。

### 3.3 金额区

- 订单金额。
- 已付金额。
- 当前待支付金额文案。

金额只展示服务端返回结果，不允许前端提交或覆盖支付金额。

### 3.4 状态区

根据后端 `status` 展示当前收款状态：

- 待支付。
- 支付确认中。
- 线下登记待确认。
- 已完成。
- 已作废/过期。

### 3.5 商品明细区

- 商品名称。
- 规格。
- 数量。
- 单价。
- 小计。

### 3.6 支付与登记区

- 在线支付。
- 线下登记备注。

本期 H5 保留 `other_paid` 入口，但它只作为线下备注登记能力。收货人提交备注和情况说明后，订单进入待确认，不允许 H5 直接把订单标记为已支付。

### 3.7 操作区

- 去支付。
- 提交线下登记。
- 刷新状态。
- 联系商户。

## 4. 接口接入流程

### 4.1 页面进入

```http
GET /pay/:token
```

用途：

- 获取订单公开详情。
- 获取当前 H5 收款状态。
- 恢复页面刷新后的真实状态。

前端处理：

- 成功后按 `data.status` 渲染页面。
- `1002` 展示不可支付。
- `40401` 展示无效链接。

### 4.2 发起在线支付

```http
POST /pay/:token/initiate
```

请求体：

```json
{}
```

成功响应中的核心字段：

```ts
{
  cashierUrl: string;
  orderId: string;
  payableAmount: string;
}
```

前端处理：

- 点击后按钮进入 loading。
- 请求未结束前禁止重复点击。
- 成功拿到 `cashierUrl` 后直接跳转。
- 跳转前可以展示“正在前往收银台”，但不能本地改写业务状态。
- 用户从第三方收银台返回后，调用 `GET /pay/:token/status` 确认最终状态。

### 4.3 查询支付状态

```http
GET /pay/:token/status
```

用途：

- 在线支付发起后轮询。
- 第三方收银台返回后确认结果。
- 用户手动刷新状态。

前端处理：

- 成功后按 `data.status` 渲染。
- `paid`、`pending_verification`、`expired` 停止自动轮询。
- `paying` 继续轮询。
- `unpaid` 按后端状态恢复待支付页面。

### 4.4 线下登记备注

```http
POST /pay/:token/offline-payment
```

本期页面语义：

- H5 只提供线下登记备注入口。
- 收货人可以备注“已与商户沟通”“现金交给某某”“需财务联系确认”等信息。
- 该入口不等于支付完成。
- 财务需要与收货人确认后，在商户端自行创建导入单或完成后续处理。
- H5 保留 `other_paid`，但只作为备注登记能力，不直接完成支付。

接口接入约束：

- 如沿用当前 `POST /offline-payment` 接口，本期 H5 只按线下备注待确认语义提交。
- `remark` 必填。
- 前端不传金额。
- 前端可以展示“其它方式已支付备注”，但提交后只进入待确认，不直接完成订单。

前端处理：

- 提交前做基础表单校验。
- 提交中禁止重复点击。
- 成功后按响应中的后端状态渲染。
- 成功后通常进入 `pending_verification`。

## 5. 状态展示规则

### 5.1 unpaid

页面行为：

- 展示“待支付”。
- 在线支付按钮可点。
- 线下登记备注入口可用。
- 默认不轮询。

注意：

- 如果刚从第三方收银台返回但仍是 `unpaid`，前端可以提示“暂未确认支付结果，请稍后刷新”。
- 前端不能因为用户曾经点击过支付就强行展示 `paying`。

### 5.2 paying

页面行为：

- 展示“支付确认中”。
- 禁用在线支付按钮。
- 禁用线下登记提交。
- 自动轮询 `/status`。
- 提供“刷新状态”按钮。

注意：

- 前端不要展示新的“去支付”主按钮，避免引导用户重复支付。
- 长时间停留 `paying` 时，提示支付结果仍以后端确认为准。

### 5.3 pending_verification

页面行为：

- 展示“线下登记待确认”。
- 提示等待商户确认。
- 禁止重复提交线下登记。
- 可提供低频刷新状态。

注意：

- 不建议高频轮询。
- 页面应突出“已提交登记，等待商户确认”，避免用户重复提交。
- 本状态不代表订单已支付完成。

### 5.4 paid

页面行为：

- 展示“付款完成”。
- 停止所有轮询。
- 刷新订单详情。
- 隐藏支付按钮。

注意：

- 如果操作接口返回 `1001`，前端也应刷新详情并展示完成态。

### 5.5 expired

页面行为：

- 区分展示“上一笔支付已过期”和“订单不可支付”。
- 如果订单仍在租户收款码有效期内，允许重新发起在线支付。
- 如果订单已作废、订单整体已过期或后端返回不可支付，则禁止在线支付和线下登记操作。
- 可展示联系客服入口。

注意：

- `expired` 支持重新支付，但必须由后端判断是否仍在租户设置的收款码有效期内。
- 当前租户通用设置字段为 `qrCodeExpiry`，位于 `tenant_general_settings`，用于表达收款码有效期覆盖值。
- `qrCodeExpiry` 当前在不同契约层存在单位描述不一致：共享 contract 写“分钟”，Swagger/DTO 写“天”。终稿落地前必须统一单位，前端不得自行用本地时间和该字段推导可支付性。

## 6. 错误码映射

| code    | 含义               | H5 行为                          |
| ------- | ------------------ | -------------------------------- |
| `1001`  | 订单已支付         | 展示完成态，立即刷新详情         |
| `1002`  | 二维码/订单已过期  | 展示不可支付，并提供联系客服入口 |
| `1003`  | 支付中             | 进入确认中，启动轮询             |
| `40001` | 支付方式非法       | 提示当前支付方式不可用           |
| `40002` | 线下登记备注为空   | 表单内提示 remark 必填           |
| `40401` | 订单不存在         | 展示无效链接                     |
| `40402` | 当前状态不允许操作 | 刷新详情，以后端状态为准         |
| `50001` | 支付网关调度失败   | 提示稍后重试，允许刷新状态       |

处理原则：

- 成功响应优先看 `data.status`。
- 异常响应按 `code` 映射页面状态。
- 遇到未知 `code`，统一提示“当前状态已变化，请刷新后重试”。
- 遇到网络错误，不改变业务状态，只展示网络异常和重试入口。

## 7. 幂等与防重复点击

前端需要做防重复点击，但不能把前端防重复当成真正幂等。

前端规则：

- 点击“去支付”后按钮进入 loading。
- 请求未结束前禁止再次点击。
- 提交线下登记时同样进入 loading 并禁用按钮。
- 收到 `1003` 时进入确认中并轮询。
- 页面刷新后重新调用 `/pay/:token` 恢复真实状态。
- 不缓存 `cashierUrl` 作为长期支付入口。

真正幂等由后端保证，前端只减少误触和重复请求。

## 8. 轮询规范

### 8.1 触发轮询的场景

- `/initiate` 成功跳转前后。
- 页面从第三方收银台返回。
- `/pay/:token` 返回 `paying`。
- `/initiate` 返回 `1003`。
- 用户点击“刷新状态”后仍返回 `paying`。

### 8.2 建议频率

```text
前 30 秒：每 2 秒一次
30 秒到 2 分钟：每 5 秒一次
2 分钟后：停止自动轮询，展示“仍在确认中，请手动刷新”
```

### 8.3 终止条件

- `paid`。
- `pending_verification`。
- `expired`。
- `40401`。
- 连续网络失败达到阈值。
- 页面离开或组件卸载。

### 8.4 轮询文案

轮询期间建议展示：

- “支付结果确认中，请勿重复支付。”
- “支付结果以后端确认为准。”
- “如果已完成支付，请稍后刷新状态。”

## 9. 弱网与异常体验

需要覆盖的异常场景：

- 请求超时。
- 网络断开。
- 页面切后台。
- 用户从支付页返回但回调未到。
- 用户关闭支付页后重新打开。
- 网关建单失败。
- 状态长时间停留 `paying`。

建议 UI：

- 顶部或状态区展示“网络不稳定，状态可能延迟”。
- 提供“刷新状态”。
- 支付中不要重新展示“去支付”主按钮。
- 长时间确认中时提示“已提交支付请求，系统正在确认结果”。
- 网络失败不改变业务状态。

## 10. UI 文案与交互建议

本项目暂无单独 H5 视觉规范，页面应优先满足清晰、克制、低误操作风险。移动端首屏应先呈现商户、金额、状态和主操作，商品明细可以折叠或放在状态后。

### 10.1 状态文案

| status                 | 主标题         | 辅助文案                                               | 主操作   |
| ---------------------- | -------------- | ------------------------------------------------------ | -------- |
| `unpaid`               | 待支付         | 请确认订单金额后完成支付。                             | 去支付   |
| `paying`               | 支付确认中     | 已发起支付请求，请勿重复支付。支付结果以后端确认为准。 | 刷新状态 |
| `pending_verification` | 登记待确认     | 已收到您的线下登记备注，商户财务确认后会继续处理。     | 刷新状态 |
| `paid`                 | 支付已完成     | 订单已完成收款。                                       | 查看订单 |
| `expired` 可重试       | 上次支付已过期 | 订单仍在有效期内，可重新发起支付。                     | 重新支付 |
| `expired` 不可支付     | 订单不可支付   | 订单已作废或收款码已超过有效期，请联系商户。           | 联系商户 |

### 10.2 按钮状态

- 主按钮一次只保留一个明确动作。
- `paying` 时不展示“去支付”主按钮。
- `paid` 时不展示支付和线下登记入口。
- `pending_verification` 时不展示重复登记入口。
- 网络失败时展示“刷新状态”，不自动改变业务状态。

### 10.3 页面布局

- 顶部：商户名称、客服电话。
- 核心区：支付状态、订单金额、已付金额。
- 操作区：根据后端状态展示主按钮和次按钮。
- 明细区：商品明细、订单号、客户、下单时间。
- 异常区：弱网、过期、无效链接、网关失败等提示。

## 11. 安全边界

H5 不传金额。

H5 不传或覆盖：

- 订单总额。
- 实收金额。
- 待支付金额。
- 手续费。
- 网关流水号。
- 支付单内部 ID。
- 支付渠道内部字段。

H5 不暴露：

- 拉卡拉字段。
- 收钱吧字段。
- 内部 `paymentOrderId`。
- 内部 payment id。
- 部分收款能力。
- 网关验签、签名、证书信息。
- 后端账务累计逻辑。

页面只展示后端允许公开的数据。

## 12. 支付渠道扩展口径

H5 页面不绑定具体支付渠道。

当前在线支付可能由拉卡拉承载，后续也可能接入收钱吧或其他渠道，但 H5 不应感知：

- 网关请求字段。
- 网关响应字段。
- 网关交易状态。
- 签名和验签规则。
- 金额单位转换。
- 第三方收银台地址字段名。

H5 只消费后端统一结构：

```ts
{
  cashierUrl: string;
  orderId: string;
  payableAmount: string;
}
```

后续新增支付渠道时，前端理想情况下不改接口流程，只由后端网关适配层完成渠道差异归一化。

## 13. 前后端动作边界

服务端不负责 UI 层面的按钮显示、隐藏、置灰和文案选择。H5 页面可以根据后端返回的 `status` 自行决定展示哪个按钮、哪个提示和是否启动轮询。

服务端负责业务动作校验。当前端调用动作接口时，服务端必须判断该动作是否允许执行，例如：

- 当前订单是否仍存在。
- 当前订单是否已支付。
- 当前订单是否已作废。
- 当前是否已有支付进行中。
- `expired` 状态是否仍处于租户 `qrCodeExpiry` 收款码有效期内。
- 线下登记是否允许提交。

因此本期不引入 `availableActions`。前端按 `status` 渲染页面，并通过动作接口结果兜底：

- `expired` 页面可以展示“重新支付”入口。
- 用户点击后调用 `POST /pay/:token/initiate`。
- 如果仍在有效期内，后端成功返回 `cashierUrl`。
- 如果已不可支付，后端返回业务错误码，前端再展示不可支付或联系商户提示。

这个边界能避免服务端掺入 UI 逻辑，同时保留服务端对支付动作的最终裁决。

## 14. 前端实现建议

### 14.1 页面状态与业务状态分离

前端可以维护 UI 状态：

- `loadingDetail`
- `submittingOnlinePayment`
- `submittingOfflineRegistration`
- `polling`
- `networkError`
- `redirecting`

前端不能维护独立业务状态机。

业务状态只来自后端：

- `unpaid`
- `paying`
- `pending_verification`
- `paid`
- `expired`

### 14.2 刷新策略

建议页面初始化时总是拉取详情：

```text
GET /pay/:token
```

以下场景重新拉取详情或状态：

- 页面可见性从隐藏变为可见。
- 从第三方收银台返回。
- 用户点击刷新。
- 操作接口返回状态变化类错误码。

### 14.3 表单约束

线下登记备注：

- `remark` 必填。
- 提交时 trim。
- 空白字符串不允许提交。
- 不允许前端传入金额。
- 允许前端提交 `other_paid` 备注登记，但不允许直接完成订单。

| 2   | token 有效，状态 `unpaid`                                  | 连续点击“去支付”        | 只允许一个 `POST /initiate` 处于提交中  | 按钮 loading，避免重复跳转                       |

| 4   | 状态 `paying`                                              | 打开页面                | `GET /pay/:token`                       | 展示支付确认中，禁用去支付和线下登记，启动轮询   |
| 5   | 状态 `paying`                                              | 轮询成功支付            | `GET /pay/:token/status`                | 状态变 `paid`，停止轮询，展示完成态              |
| 6   | 状态 `paying`                                              | `/initiate` 返回 `1003` | `POST /pay/:token/initiate`             | 展示确认中并轮询                                 |
| 7   | 状态 `paid`                                                | 打开页面                | `GET /pay/:token`                       | 展示完成态，不展示支付入口                       |
| 8   | 状态 `paid`                                                | 再次发起支付            | `POST /pay/:token/initiate` 返回 `1001` | 刷新详情，展示完成态                             |
| 9   | 状态 `unpaid`                                              | 提交线下登记备注        | `POST /pay/:token/offline-payment`      | 成功后展示 `pending_verification` 或后端返回状态 |
| 10  | 状态 `unpaid`                                              | 空备注提交线下登记      | 前端拦截或后端返回 `40002`              | 表单内提示备注必填                               |
| 11  | 状态 `pending_verification`                                | 打开页面                | `GET /pay/:token`                       | 展示登记待确认，不允许重复登记                   |
| 12  | 状态 `pending_verification`                                | 点击刷新                | `GET /pay/:token/status`                | 仍按后端状态展示，不高频轮询                     |
| 13  | 上一笔支付尝试 `expired`，订单仍在 `qrCodeExpiry` 有效期内 | 点击重新支付            | `POST /pay/:token/initiate`             | 成功返回 `cashierUrl` 并跳转                     |
| 14  | 订单已作废或超过收款码有效期                               | 打开页面                | `GET /pay/:token` 或 `/status`          | 展示不可支付，禁止支付和登记                     |

| 18  | 网络超时                                                   | 任意请求                | 请求失败                                | 展示弱网提示，不改变业务状态                     |
| 19  | 页面切后台后返回                                           | 页面重新可见            | `GET /pay/:token/status`                | 用后端最新状态恢复页面                           |
| 20  | 后端返回未知错误码                                         | 任意操作                | 任意接口                                | 提示刷新后重试，不推进本地状态                   |

## 16. 待确认问题

以下问题建议在进入正式开发前确认：

1. `qrCodeExpiry` 的单位需要统一。当前共享 contract 写“分钟”，Swagger/DTO 写“天”。
2. H5 线下登记是否沿用当前 `POST /offline-payment` 接口，还是新增更贴合语义的“登记备注”接口。
3. 商户客服电话是否必展示，以及优先使用 `tenant.generalSettings.contactPhone` 还是 `tenant.contactPhone`。
