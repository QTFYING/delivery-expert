# API 项目 Review 清单（2026-04-23）

> 文档状态：历史评审稿，已归档

> 评审对象：`apps/api`、`packages/types`、`docs/api`、`schema.prisma`
> 评审目标：从资深后端视角梳理当前项目在支付安全、金额一致性、导入恢复、多租户隔离上的高风险问题，并给出可执行修复清单。

---

## 一、评审结论

本次 review 的核心结论不是“代码风格还可以优化”，而是当前项目在“钱”和“状态”相关链路上，存在几处必须优先处理的实质性风险：

1. Webhook 信任边界过宽
2. 人工/异步入账链路幂等不足
3. 订单金额口径与财务流水口径不一致
4. 导入任务恢复机制与设计预期不一致

建议修复优先级：

1. 先堵安全漏洞
2. 再补幂等与金额一致性
3. 最后补恢复性与测试覆盖

---

## 二、问题清单

### P0-1 Webhook 未验签且未校验金额

**问题位置**

- `apps/api/src/payment/payment.controller.ts`
- `apps/api/src/payment/payment.service.ts`
- `docs/api/api-architecture-overview.md`

**问题描述**

- 公开回调接口 `POST /payment/webhook/lakala` 当前未见签名校验
- 未校验回调金额是否与订单/支付单金额一致
- 当 `gatewayTradeNo` 缺失时，还会 fallback 到 `orderId + 最近一笔 PAYING 支付单`

**风险**

- 任意伪造回调可能把订单改成已支付
- 缺失网关交易号时可能误入账
- 与文档“后端校验拉卡拉签名”的约束不一致

**修复建议**

1. 强制验签，不通过直接拒绝
2. 强制校验网关交易号、订单号、支付金额
3. 禁止使用“仅凭 orderId 找最近一笔支付单”的兜底逻辑
4. 把回调解析字段收敛成明确 DTO，不接受任意 shape

**验收清单**

- 无签名请求返回失败
- 签名错误请求返回失败
- 金额不一致请求返回失败
- 缺失 `gatewayTradeNo` 请求不允许入账
- 合法重复回调只产生一次支付流水

### P0-2 现金核销缺少强幂等，可能重复记账

**问题位置**

- `apps/api/src/payment/payment.service.ts#createCashVerification`

**问题描述**

- 先查 `PENDING_VERIFICATION`
- 再更新支付单状态
- 再插入 `payments`
- 再更新 `orders.paid`

整个过程没有基于旧状态的条件更新，也没有唯一幂等键或版本控制。

**风险**

- 并发核销时，可能插入两条支付流水
- `payments` 金额与 `orders.paid` 金额可能不一致
- 财务汇总按 `payments` 聚合，订单详情按 `orders.paid` 展示，最终形成两套账

**修复建议**

1. 核销更新改为条件更新：仅允许 `status = pending_verification` 时更新成功
2. 以支付单 ID 作为核销幂等锚点，防止重复插入流水
3. 若条件更新返回 0，应视为已核销或状态已变化
4. 为“支付单已核销生成收款流水”建立唯一约束或显式幂等表述

**验收清单**

- 同一笔现金核销并发提交只成功一次
- 重试请求返回已处理，不新增第二条支付流水
- `payments` 汇总金额与 `orders.paid` 始终一致

### P1-1 手工建单/改单允许直接写 `paid` 与 `status`

**问题位置**

- `apps/api/src/order/dto/create-order.dto.ts`
- `apps/api/src/order/dto/update-order.dto.ts`
- `apps/api/src/order/order.service.ts`
- `apps/api/src/finance/finance.service.ts`

**问题描述**

- 手工建单和改单接口允许调用方直接传 `paid`
- 也允许直接传 `status`
- 但财务汇总和对账依赖 `payments` 表，而不是 `orders.paid`

**风险**

- 可以造出“订单已支付，但没有任何收款流水”的数据
- 订单列表、支付页、财务汇总三套口径不一致
- 后续对账、稽核、导出都可能出现解释不通的数据

**修复建议**

1. 普通建单/改单接口禁止直接写 `paid` 和 `status`
2. 收款动作统一走支付回调、现金核销、账期回款等显式入账接口
3. `orders.status` 由领域规则推导，不由外部请求直接指定
4. 如确需历史数据迁移入口，应单独做受限管理接口，不混在业务 API 中

**验收清单**

- 手工建单默认 `paid = 0`
- 手工改单不能直接把订单改成 `paid`
- 每一笔入账都能在 `payments` 找到对应流水
- 财务汇总与订单已收金额可交叉对平

### P1-2 账期回款同样存在重复入账风险

**问题位置**

- `apps/api/src/order/order.service.ts#createReceipt`

**问题描述**

- 账期回款会直接插入 `payments`
- 然后更新 `orders.paid`
- 当前没有显式幂等键，也没有并发重复提交保护

**风险**

- 前端重复点击/超时重试时，可能生成多笔回款记录
- 与现金核销类似，存在支付流水与订单实收金额错位风险

**修复建议**

1. 账期回款增加请求级幂等能力
2. 或引入单据型“回款记录”作为唯一业务实体，再由其驱动 `payments`
3. 增加并发提交测试与数据库唯一性保障

**验收清单**

- 同一回款请求重复提交只落一次账
- 并发提交不会生成两条相同语义的回款流水

---

### P1-3 导入任务恢复机制名义 2 分钟，实际可能卡 30 分钟

**问题位置**

- `apps/api/src/import/import.service.ts`
- `apps/api/src/redis/redis.service.ts`

**问题描述**

- 导入任务 stale 判定阈值为 2 分钟
- 但执行锁 TTL 是 30 分钟
- worker 心跳只写数据库，不续租 Redis 锁

**风险**

- worker 崩溃后，任务虽然会被标记成 stale
- 但新 worker 仍可能 30 分钟内拿不到锁
- 用户看到任务长时间停在 `processing`

**修复建议**

1. 心跳时同步续租执行锁
2. 或缩短执行锁 TTL，并通过定时续租维持活锁
3. 明确“stale 判定时间”与“锁失效时间”的一致性策略

**验收清单**

- worker 异常退出后，任务能在预期时间内被重新拾起
- 不会出现数据库判 stale、Redis 仍持锁的长时间卡死状态

### P2-1 关键链路缺少自动化测试兜底

**问题位置**

- 仓库内未检索到针对以下链路的关键测试：
  - `handleLakalaWebhook`
  - `createCashVerification`
  - `createReceipt`
  - `submitOrderImport / processImportJob`

**问题描述**

- 当前高风险链路大多依赖人工阅读保证正确性
- 缺少并发、重试、重复回调、错误金额等反例测试

**风险**

- 修 bug 时容易引入回归
- 很难证明“幂等”和“金额一致性”已经真正收口

**修复建议**

1. 优先补 4 类高价值测试：
   - webhook 验签/重复回调
   - 现金核销并发幂等
   - 账期回款重复提交
   - 导入任务中断恢复
2. 优先做 service 层集成测试，不先铺大量低价值 unit test

**验收清单**

- 关键资金链路都有失败分支测试
- 并发/重试场景有回归用例
- 修复后新增测试能稳定复现旧 bug 并证明已修复

## 三、建议执行顺序

### 第一阶段：立即处理

1. 封堵 webhook 未验签问题
2. 移除 webhook 的弱 fallback 入账逻辑
3. 给现金核销补条件更新与幂等收口

### 第二阶段：本周内处理

1. 禁止普通订单接口直接写 `paid` / `status`
2. 梳理订单状态唯一推导路径
3. 给账期回款补幂等保护

### 第三阶段：稳定性加固

1. 修正导入任务锁与心跳策略
2. 增补关键链路集成测试
3. 为支付、核销、导入增加更明确的审计与告警

---

## 四、建议的开发原则

后续这类链路统一遵守：

1. 任何“入账”动作都必须有唯一业务锚点
2. 任何“状态变更”都必须可证明只会发生一次
3. 任何“订单已收金额”都必须能被 `payments` 事实表对平
4. 任何“异步任务恢复”都必须让锁、心跳、状态三者一致
5. Controller 不做业务判断，Service 不散落持久化语义，金额与状态机规则集中管理

---

## 五、最终建议

如果只做一件事，先修 webhook。

如果做一个小迭代，建议打一个“资金链路安全与一致性修复包”，最少包含：

1. webhook 验签 + 金额校验
2. 现金核销幂等
3. 禁止手工订单直接写 `paid/status`
4. 账期回款幂等
5. 关键链路测试补齐

这样才能把这个项目从“能跑”提升到“账不容易出事故”。
