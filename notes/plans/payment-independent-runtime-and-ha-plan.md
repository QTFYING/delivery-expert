# 支付独立运行与高可用演进计划

> 日期：2026-05-19
> 文档状态：方案讨论稿
> 文档定位：部署与架构演进计划，属于 `notes` 非事实源，不直接定义接口语义或数据模型
> 适用范围：`apps/api` 支付链路、生产发布流程、数据库迁移流程、单机 ECS 到多 ECS 的扩展路径

## 一、背景与痛点

当前系统有三个业务核心：

1. 订单预检和导入
2. 订单支付
3. 对账

其中订单支付的业务变化频率最低，但可用性要求最高。实际线上痛点是：系统其它内容更新时，尤其涉及数据库迁移、API 重启或容器重建时，会导致支付入口不可用，进而影响客户扫码付款和第三方支付回调。

这个问题不应只靠“发版时动作快一点”解决，而应把支付链路从主系统发布节奏中拆出来，并配套建立数据库零停机迁移原则。

## 二、核心结论

推荐采用“支付高可用最小闭环”，不一开始拆完整微服务。

当前阶段的正确方向是：

1. 在同一个代码仓内新增独立 `payment-api` 运行时。
2. 主 `api` 和 `payment-api` 分开启动、分开发版、分开重启。
3. 对外域名和接口路径保持不变，通过 Nginx/OpenResty 按路径分流。
4. 数据库迁移遵循 expand/contract 零停机规则，禁止生产环境破坏性直改。
5. 所有运行状态放到 PostgreSQL、Redis 或 OSS，不依赖 ECS 本机内存或本机磁盘。

## 三、目标与非目标

### 3.1 目标

- 普通后台 API 发版时，不影响 H5 支付页、发起支付、支付状态查询和支付回调。
- 数据库迁移不再因为其它业务表调整而拖死支付核心链路。
- 支付回调可落库、可追踪、可重放，避免第三方重复通知或短暂异常导致账务事实丢失。
- 单机 ECS 阶段的部署形态可以平滑演进到多 ECS 横向扩展。

### 3.2 非目标

- 不立即把支付拆成独立仓库。
- 不立即拆独立支付数据库。
- 不立即引入复杂服务治理、注册中心或完整微服务体系。
- 不因为支付独立运行而改变现有对外接口路径。

## 四、单机 ECS 目标部署形态

当前 `api` 项目对外监听 `3000`。新增独立支付运行时后，推荐在同一台 ECS 上使用不同本机端口：

```text
Nginx/OpenResty : 80/443
api             : 127.0.0.1:3000
payment-api     : 127.0.0.1:3001
import-worker   : 不暴露端口
PostgreSQL      : 1Panel 托管或云托管
Redis           : 1Panel 托管或云托管
```

对外仍保持同一个域名和路径：

```text
/api/pay/*                 -> payment-api
/api/payment/webhook/*     -> payment-api
/api/*                     -> api
```

前端和第三方支付配置不需要感知 `3001`。第三方回调地址仍保持：

```text
https://api.example.com/api/payment/webhook/lakala
```

## 五、支付独立运行时边界

独立 `payment-api` 应只加载支付最小闭环，不承载后台管理、导入、对账报表等非支付能力。

### 5.1 建议保留的入口

- `GET /api/pay/:token`
- `POST /api/pay/:token/initiate`
- `GET /api/pay/:token/status`
- `POST /api/payment/webhook/lakala`
- 可选：`POST /api/pay/:token/offline-payment`

### 5.2 可继续留在主 API 的入口

- Tenant 后台订单管理
- Tenant 财务对账
- Admin 跨租户流水查询
- 导入预检和正式导入
- 打印、催款、统计报表
- 支付渠道配置管理

支付渠道配置管理是否进入 `payment-api` 要谨慎。它是后台管理动作，不是客户支付闭环；通常留在主 `api` 更合适。`payment-api` 只读取当前生效配置。

## 六、数据库零停机迁移原则

支付独立运行只能解决“应用进程重启导致支付不可用”的问题；如果数据库迁移锁表或破坏兼容，支付仍会不可用。因此必须配套生产迁移规则。

### 6.1 生产环境禁止项

- 禁止生产直接使用 `prisma db push`。
- 禁止直接删除支付正在读取的字段。
- 禁止直接重命名支付正在读取的字段。
- 禁止直接把大表字段改为 `NOT NULL` 且无安全默认值。
- 禁止在大表上执行可能长时间强锁的 DDL。
- 禁止把支付状态、金额、租户边界字段做不兼容改义。

### 6.2 推荐迁移流程

所有涉及线上表结构的变更，默认使用：

```text
expand -> 双版本兼容 -> backfill -> switch read -> contract
```

含义如下：

1. `expand`：只新增兼容字段、兼容表、兼容索引。
2. 双版本兼容：旧代码和新代码都能在同一套数据库结构上运行。
3. `backfill`：需要历史数据时，使用小批量异步回填，不在 DDL 中一次性重写大表。
4. `switch read`：确认新字段稳定后，再切换读取来源。
5. `contract`：最后一个发布周期再删除旧字段或旧逻辑。

### 6.3 PostgreSQL 注意事项

- 大表新增索引优先使用 `CREATE INDEX CONCURRENTLY`。
- 回填脚本要分批执行，并控制事务大小。
- 支付核心表迁移前必须评估锁级别和执行时间。
- migration SQL 进入生产前必须人工 review。
- Prisma schema 可以作为目标模型，但生产执行 SQL 需要单独审查。

### 6.4 支付核心表保护清单

以下表被视为支付高风险依赖，迁移必须优先保证兼容：

- `orders`
- `payment_orders`
- `payments`
- `payment_webhook_events`
- `tenant_payment_configs`
- `tenants`

涉及这些表时，必须额外确认：

- 金额字段仍使用 `Decimal`。
- 支付回调幂等键仍有物理唯一约束或等价约束。
- 租户字段与查询索引不被破坏。
- 支付状态机不会出现旧代码无法识别的新状态。

## 七、支付回调可靠性要求

支付回调是最不能丢的入口。推荐把回调处理稳定成两段式：

```text
第三方回调
  -> payment-api 接收原始请求
  -> 验签与归一化
  -> 写入 payment_webhook_events
  -> 幂等处理支付单与流水
  -> 返回第三方要求的响应
```

最低要求：

1. 回调必须记录原始请求、验签结果、归一化结果和处理状态。
2. 重复回调不会重复累计订单实收金额。
3. 入账动作必须能通过 `payment_orders`、`payments`、`payment_webhook_events` 解释同一事实。
4. 处理失败的回调必须可人工排查，并具备后续重放空间。
5. 第三方回调入口不依赖主 `api` 是否正在发版。

## 八、未来多 ECS 横向扩展要求

单机阶段如果按以下规则建设，后续扩展到多台 ECS 会比较顺。

### 8.1 目标形态

```text
SLB / Nginx
  /api/pay/*                 -> payment-api-1, payment-api-2
  /api/payment/webhook/*     -> payment-api-1, payment-api-2
  /api/*                     -> api-1, api-2

共享 PostgreSQL
共享 Redis
共享 OSS
```

### 8.2 服务必须无状态

`api` 和 `payment-api` 不应依赖本机内存保存业务状态。

必须放到共享基础设施的内容：

- 登录会话或 token 状态
- 支付单状态
- 支付回调处理状态
- 导入任务状态
- 分布式锁
- 导出文件、导入文件、支付凭证或附件

### 8.3 幂等不能依赖单机锁

多台 `payment-api` 同时收到重复请求时，必须由数据库唯一约束、事务条件更新和共享 Redis 锁兜底。

支付链路重点保护：

- 用户重复点击发起支付
- 第三方重复回调
- 回调与状态查询并发
- 线下登记与在线回调并发
- 财务核销与旧支付回调并发

### 8.4 Worker 必须可多实例抢占

`import-worker` 后续可以多实例，但必须依赖数据库任务状态或 Redis 分布式锁抢占任务，不能靠单进程内存判断。

导入任务需要保证：

- 同一个任务不会被两个 worker 同时执行。
- 卡在中间态的任务可以被恢复。
- 失败重试、最终失败、人工排查有明确状态。

### 8.5 文件不能落 ECS 本机

如果后续出现导入文件、导出对账单、支付凭证、图片附件，推荐进入 OSS。

不要让业务依赖本机路径，否则多 ECS 后会出现某台机器可读、另一台机器不可读的问题。

## 九、建议落地阶段

### T01 支付运行时拆分

目标：

- 新增独立 `payment-api` 启动入口。
- 只加载支付最小闭环 controller/service/provider。
- 主 `api` 与 `payment-api` 可独立启动。

完成标准：

- 本地可同时启动 `api:3000` 与 `payment-api:3001`。
- 支付 H5 详情、发起支付、状态查询、Webhook 路由可在 `payment-api` 上工作。
- 主 `api` 停止时，`payment-api` 仍可处理支付入口。

### T02 网关路径分流

目标：

- Nginx/OpenResty 按路径把支付请求转发到 `payment-api`。
- 对外域名和路径保持不变。

完成标准：

- `/api/pay/*` 命中 `payment-api`。
- `/api/payment/webhook/*` 命中 `payment-api`。
- 其它 `/api/*` 命中主 `api`。

### T03 生产迁移规范落地

目标：

- 明确生产禁止 `prisma db push`。
- 建立 migration SQL review 流程。
- 对支付核心表建立迁移前检查清单。

完成标准：

- 每次涉及数据库迁移的发布都能说明是否影响支付核心表。
- 迁移脚本满足 expand/contract 原则。
- 支付运行时与主 API 至少能跨一个版本兼容。

### T04 回调审计与重放能力增强

目标：

- 强化 `payment_webhook_events` 作为回调事实入口。
- 明确失败回调的排查与重放路径。

完成标准：

- 回调处理失败可查询原因。
- 重复回调不会重复入账。
- 必要时可以针对失败事件重新触发处理。

### T05 多 ECS 准备

目标：

- 清理本机状态依赖。
- 验证 Redis、PostgreSQL、OSS 均为共享基础设施。
- 为 `api` 和 `payment-api` 多实例部署做准备。

完成标准：

- 任意一台应用实例重启，不影响其它实例接管请求。
- 支付幂等不依赖单机内存。
- Worker 多实例不会重复执行同一个任务。

## 十、验收检查表

发布与部署：

- `api` 和 `payment-api` 可以独立部署。
- 主 `api` 重启时，支付路径仍可访问。
- 第三方回调地址不需要变化。
- Nginx/OpenResty 分流规则有明确配置。

支付安全：

- 服务端计算支付金额，前端不传可篡改金额。
- 支付回调幂等。
- 支付流水不会重复累计。
- 订单状态、支付单状态、支付流水、Webhook 事件能相互解释。

数据库迁移：

- 生产不使用 `prisma db push`。
- migration SQL 经过 review。
- 支付核心表迁移满足兼容原则。
- 大表索引使用在线方式创建。

横向扩展：

- API 进程无本机状态依赖。
- 分布式锁使用共享 Redis。
- 业务文件进入 OSS 或等价共享存储。
- 多 worker 场景下任务不会重复消费。

## 十一、当前推荐决策

当前最适合的决策是：

1. 先在单机 ECS 上拆出 `payment-api`，端口使用 `3001` 或容器内 `3000` 映射到宿主 `3001`。
2. 对外路径不变，只在 Nginx/OpenResty 做内部路径分流。
3. 同步建立生产数据库迁移规范，尤其保护支付核心表。
4. 暂不拆独立支付数据库，等流量、团队规模和运维能力需要时再升级。
5. 现在就按无状态服务要求建设，为未来多 ECS 扩容留好路。
